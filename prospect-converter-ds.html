Components

Components are reusable interface elements with variations and states. Unique components include extra rules. Basic structure was, component - variants - states - additional rules + links.

Patterns

Patterns show how existing components work together as part of a bigger interface. For example, the “Changes Saving” pattern explains what happens when a user edits something and saves it. It shows when to use it, like in forms or settings.

Interaction like this is listed step by step with screen examples, showing how the components behave. Instead of repeating rules, each step links to the components already described elsewhere.

Form Guideline For Devs Team

The goal was to help developers build forms without designing full screens, avoiding extra work and communication. Guideline explains which components can be used, how to choose the right ones, and rules for their placement relative to each other. All necessary variations were covered, including single controls, control or text groups, and subgroups.

Key challenges

Components status Tracking

While working within a team of up to 5 designers, we had a struggle to understand if we could reuse a particular component or not. So, on one of team retrospective workshop sessions, we decided marking statuses for each component. Which saved us time spent on communications.

Form Guideline

We designed many forms, that has a lot of common rules. On one of our weekly syncs with the Dev team, together we came up with the idea to prepare such a “Guideline”.

Dates and titles formatting

At some point I spotted that there are inconsistencies in terms of dates formatting. So I requested a team sync to set up a rules group, and document them after discussion. Important to mention – that such rules are “nice to have” as a link, on the pages of related components.
